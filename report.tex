\section{Introduction}
%─────────────────────────────────────────────────────────────────────────────

This report presents the system architecture, implementation details, and empirical benchmark evaluation for \textbf{Lab 6: Dynamic Load Balancing and Persistent Chat}. The goal of this assignment is to extend a secure, persistent group-chat backend into a horizontally scaled, distributed application deployed across three dedicated lab machines behind a unified Load Balancer.

\subsection{Evolution from Round-Robin to Dynamic Load Balancing}

At the inception of this project, the deployment relied on a basic static \textbf{Round-Robin} load balancer. While static Round-Robin provides naive distribution across operational nodes, it operates blindly without feedback regarding actual machine state. Under heavy burst traffic, heterogeneous query costs (such as broad database fetches versus lightweight message posts), or localized resource contention, Round-Robin inevitably routes traffic into bottlenecked backends, resulting in elevated tail latencies ($p_{99}$) and request dropouts.

To address these limitations, we upgraded the system to a \textbf{Performance-Based Dynamic Load Balancer} powered by the \emph{Power-of-Two-Choices (P2C)} algorithm. The upgraded balancer continuously monitors real-time telemetry from each backend node---including active in-flight HTTP requests, CPU utilization percentage, active WebSocket connections, and Valkey database round-trip time (RTT). By dynamically evaluating a composite load score, the load balancer intelligently routes incoming traffic away from saturated nodes, optimizes system throughput, and automatically isolates unresponsive or failing backends.

\subsection{Assignment Scope and Requirements}

The implementation strictly satisfies all core directives outlined in the Lab 6 specification:

\begin{enumerate}[label=\textbf{\arabic*.}]
    \item \textbf{Three-Node Backend Deployment}: Deploy the backend application across three designated backend systems (\texttt{Sys2}, \texttt{Sys3}, and \texttt{Sys4}). All client traffic enters through a single Load Balancer entrypoint on \texttt{Sys1}.
    \item \textbf{Performance-Based Dynamic Load Balancing}: Replace fixed Round-Robin with dynamic metric-driven routing. Automatically detect unhealthy or degraded backends and suspend traffic delivery to them.
    \item \textbf{Threshold and Routing Optimization}: Define and tune optimal load-switching thresholds to maximize throughput and minimize request latency under high concurrency.
    \item \textbf{Shared Database Persistence and Strict Deduplication}: All backend instances must access a shared persistent data layer. Every message is assigned a unique message ID (\texttt{msg\_id}), ensuring strict idempotency and duplicate prevention across retries and failovers.
    \item \textbf{Standardized API Routes}: Expose exact required gateway routes:
    \begin{itemize}
        \item \texttt{POST /message} --- Ingests chat messages with \texttt{client-name} and \texttt{msg} fields.
        \item \texttt{GET /feed} --- Retrieves persistent chat messages chronologically.
    \end{itemize}
    \item \textbf{Custom Load Generator and Comprehensive Evaluation}: Construct a high-concurrency custom load generator in Go to simulate variable user counts, message lengths, and inter-request intervals, generating comprehensive performance plots across single-backend, Round-Robin, and dynamic load balancing topologies.
    \item \textbf{Preservation of Security and Baseline Features}: Maintain all prior secure application capabilities (AES-GCM encryption, ECDSA digital signatures, HMAC-SHA256 integrity verification, and WebSocket streaming) without simplification or removal.
\end{enumerate}

\subsection{Data Flow}

\begin{enumerate}
    \item A client sends \texttt{POST /message} to the Load Balancer (\texttt{:5269}).
    \item The LB selects a backend using Power of Two Choices (P2C) based on a composite load score.
    \item The selected backend writes atomically to the \textbf{Valkey primary} (Sys2) via a Lua script that prevents duplicate insertion.
    \item Valkey asynchronously replicates the write to replicas on Sys3 and Sys4.
    \item \texttt{GET /feed} reads from the \textbf{local replica}, keeping read latency minimal.
    \item SQLite (local to each machine) is retained for user accounts, rooms, XP, and session tokens.
\end{enumerate}

\subsection{Shared Message Store: \texttt{server/feed\_store.py}}

\subsubsection{Design Rationale}

SQLite is a single-writer, file-based database not designed for concurrent writes from multiple independent processes across different machines. \textbf{Valkey} (a BSD-licensed open-source fork of Redis) is used for the message hot-path because:
\begin{itemize}
    \item It operates entirely in-memory, delivering sub-millisecond RTT under normal conditions.
    \item It natively supports primary-replica asynchronous replication, making cross-backend data sharing transparent.
    \item Its \texttt{HSETNX} command enables atomic, idempotent message insertion without application-level locking.
    \item Lua scripting allows multi-step operations to execute atomically on the server.
\end{itemize}

SQLite is retained for user accounts, authentication tokens, and room metadata which are local to each node.

\subsubsection{Data Model}

\begin{center}
\begin{tabular}{lll}
\toprule
\textbf{Key pattern} & \textbf{Type} & \textbf{Contents} \\
\midrule
\texttt{msg:\{room\_id\}} & Hash & \texttt{msg\_id} $\to$ JSON-encoded message payload \\
\texttt{msgorder:\{room\_id\}} & Sorted Set & \texttt{msg\_id} scored by \texttt{created\_at\_ts} (Unix epoch) \\
\bottomrule
\end{tabular}
\end{center}

This pairing enables $O(1)$ lookup of any message and $O(\log N + M)$ range queries for history retrieval.

\subsubsection{Atomic Deduplication via Lua Script}

\begin{lstlisting}[language=Python, caption={Lua script in feed\_store.py for atomic idempotent insertion}]
_LUA_INSERT = """
local inserted = redis.call('HSETNX', KEYS[1], ARGV[1], ARGV[2])
if inserted == 1 then
    redis.call('ZADD', KEYS[2], ARGV[3], ARGV[1])
end
return inserted
"""
\end{lstlisting}

\texttt{HSETNX} sets the field only if it does not already exist. If a \texttt{msg\_id} is already present (from a retry or a duplicate delivery through another backend), the script returns \texttt{0} and skips the \texttt{ZADD}. Because Lua scripts execute atomically within a single Valkey event-loop cycle, there is no race condition between the existence check and the insertion.

\subsubsection{Paginated Read with Replica Fallback}

The \texttt{get\_all()} function retrieves the latest $N$ messages by pushing the pagination limit directly into the Valkey \texttt{ZRANGE} query:

\begin{lstlisting}[language=Python, caption={Paginated fetch with primary fallback in feed\_store.py}]
async def get_all(room_id: str, limit: int = 0) -> List[Dict]:
    # ZRANGE -N -1 returns the latest N entries from the sorted set
    start_rank = -limit if limit > 0 else 0

    try:
        msg_ids  = await _replica.zrange(f"msgorder:{room_id}", start_rank, -1)
        if not msg_ids:
            return []
        payloads = await _replica.hmget(f"msg:{room_id}", msg_ids)
    except Exception:
        # Replica unavailable -- fall back to primary to avoid HTTP 500
        msg_ids  = await _primary.zrange(f"msgorder:{room_id}", start_rank, -1)
        if not msg_ids:
            return []
        payloads = await _primary.hmget(f"msg:{room_id}", msg_ids)

    return [json.loads(p) for p in payloads if p]
\end{lstlisting}

\begin{notebox}
\textbf{Design decision --- primary fallback:} When the local Valkey replica is temporarily unavailable, \texttt{/feed} falls back to reading from the primary rather than returning an HTTP 500 error. This ensures service continuity at the cost of a slightly longer network round-trip, which is preferable to a complete service failure.
\end{notebox}

\subsection{Duplicate Prevention: Three-Layer Defence}

\begin{center}
\begin{tabular}{clll}
\toprule
\textbf{Layer} & \textbf{Mechanism} & \textbf{Scope} & \textbf{Location} \\
\midrule
1 & Lua \texttt{HSETNX} & Cross-backend (shared Valkey primary) & \texttt{feed\_store.py} \\
2 & SQLite \texttt{UNIQUE INDEX} & Per-node structural guarantee & \texttt{db.py} schema \\

\subsection{Load Balancer}

\subsubsection{Composite Load Score}

Each backend is assigned a scalar load score combining four metrics:

\begin{equation}
\text{score} = 2 \cdot \text{in-flight} + \text{CPU\%} + 0.5 \cdot \text{WS connections} + 3 \cdot \text{Valkey RTT (ms)}
\end{equation}

The weights reflect the relative impact on end-to-end request latency:
\begin{itemize}
    \item \textbf{In-flight} ($\times 2$): The most direct real-time signal of current backend load.
    \item \textbf{CPU\%} ($\times 1$): OS-level compute saturation.
    \item \textbf{WebSocket connections} ($\times 0.5$): Background load from persistent connections.
    \item \textbf{Valkey RTT} ($\times 3$): Heaviest weight because every \texttt{/message} write and \texttt{/feed} read involves a Valkey round-trip. A congested database path directly translates to elevated end-to-end response times.
\end{itemize}

\subsubsection{Overload Detection}

A backend is considered overloaded when its live in-flight request count exceeds the threshold:

\begin{lstlisting}[language=Go, caption={Real-time overload detection using atomic in-flight counter}]
const overloadThreshold int64 = 200

func (b *Backend) IsOverloaded() bool {
    return b.inFlight.Load() > overloadThreshold
}
\end{lstlisting}

Using the real-time in-flight counter rather than stale health-check scores prevents the Thundering Herd problem: when a backend recovers, the score drops immediately in the health check which could cause all traffic to flood back simultaneously. The live atomic counter gives a continuously accurate picture of load.

\subsubsection{Power of Two Choices (P2C) Algorithm}

\begin{lstlisting}[language=Go, caption={P2C backend selection in nextBackend() -- main.go}]
// Pick two distinct random backends
i := rand.Intn(n)
j := rand.Intn(n - 1)
if j >= i { j++ }

b1, b2 := lb.backends[i], lb.backends[j]

if b1.IsAlive() && !b1.IsOverloaded() &&
   b2.IsAlive() && !b2.IsOverloaded() {
    if b1.InFlightCount() <= b2.InFlightCount() {
        return b1
    }
    return b2
} else if b1.IsAlive() && !b1.IsOverloaded() {
    return b1
} else if b2.IsAlive() && !b2.IsOverloaded() {
    return b2
}
// Fallback: round-robin among alive backends
\end{lstlisting}

\begin{infobox}
\textbf{Why P2C?} Pure random selection has an expected maximum load of $O(\log n / \log \log n)$ across $n$ backends. P2C reduces this to $O(\log \log n)$ --- an exponential improvement --- by sampling two candidates and picking the lighter one. This is achieved in $O(1)$ with no synchronisation required.
\end{infobox}

\subsubsection{Health Monitoring Loop}

A background goroutine polls each backend's \texttt{/health} endpoint every 5 seconds:

\begin{lstlisting}[language=Go, caption={Health loop updating alive status and load score atomically}]
resp, err := client.Get(b.URL.String() + "/health")
if err != nil || resp.StatusCode != http.StatusOK {
    b.SetAlive(false)
    b.SetLoadScore(9999.0)  // penalty score: never selected
} else {
    var h BackendHealth
    json.NewDecoder(resp.Body).Decode(&h)
    b.SetLoadScore(b.computeLoadScore(h))
    b.SetAlive(true)
}
\end{lstlisting}

Dead backends receive a penalty score of \textbf{9999}, ensuring they are never selected by P2C. When a backend recovers, it is immediately marked alive on the next health-check cycle.

\subsection{Valkey Persistence}

The Valkey primary uses Append-Only File (AOF) persistence with \texttt{everysec} fsync:

\begin{lstlisting}[language=bash, caption={scripts/valkey\_primary.sh --- AOF persistence}]
redis-server --daemonize yes --bind 0.0.0.0 --port $PORT \
    --appendonly yes \
    --appendfilename valkey.aof \
    --appendfsync everysec \
    --no-appendfsync-on-rewrite yes \
    --save ""
\end{lstlisting}

\texttt{appendfsync everysec} flushes the AOF buffer to disk once per second in a background thread while replying to clients immediately, providing a maximum one-second data-loss window in the event of a system failure.

\paragraph{Analysis.}
The load-balanced mixed workload achieves \textbf{492 RPS} compared to \textbf{206 RPS} on a single backend, a \textbf{2.4$\times$ increase}. The LB write experiment (445 RPS) outperforms single-backend write (354 RPS) by 26\% per backend: since all three backends issue writes to the shared Valkey primary in parallel, the bottleneck shifts from the backend tier to the database tier. Read throughput scales near-linearly (161 RPS single vs.\ 328 RPS LB, a 2.0$\times$ improvement) because each backend's local replica serves reads independently with no cross-machine coordination.

\begin{figure}[H]

\paragraph{Analysis.}
Median (p50) write latency drops from \textbf{488\,ms} on a single backend to \textbf{309\,ms} under the load balancer, a 37\% reduction. The most striking result is tail latency: p99 for the single-backend mixed workload reaches \textbf{3,245\,ms}, compared to \textbf{1,710\,ms} under the LB --- a 47\% improvement. This demonstrates that P2C effectively prevents any single backend from becoming a bottleneck that degrades tail latency for all concurrent users.

Median read latency under the LB (\textbf{464\,ms}) is 57\% lower than the single-backend read (\textbf{1,080\,ms}). When 200 concurrent clients simultaneously request \texttt{/feed} from a single backend, all 200 queries hit the same local replica. Distributing across three backends reduces per-replica concurrency approximately three-fold.

Reads are inherently slower than writes in this system because a write is a single Lua script execution on the primary, while a read involves a \texttt{ZRANGE} (to retrieve ordered message IDs) followed by an \texttt{HMGET} (to retrieve payloads), plus JSON serialisation of the response body.

\subsection{Dropout Rate}

\begin{figure}[H]
    \centering
    \includegraphics[width=0.92\textwidth]{dropout_comparison.png}
    \caption{Request dropout rate across all experiments. The single-backend mixed workload exhibits a 2.15\% dropout rate, which the load balancer eliminates entirely in the equivalent configuration.}
\end{figure}

\paragraph{Analysis.}
Under mixed workload on a single backend, \textbf{429 out of 20,000 requests failed} (2.15\% dropout). This occurs because 200 concurrent clients simultaneously issuing both write and read requests exhausts the backend's connection pool and causes request timeouts. The load balancer completely eliminates this in the equivalent mixed experiment, achieving \textbf{0.00\% failure rate} with 20,000 successful responses. The small residual dropout in \texttt{lb\_write} (0.61\%) and \texttt{lb\_read} (0.03\%) is attributable to transient network events during the experiment; the load generator does not retry failed requests by design, so these represent true one-off failures, not systematic degradation.

\section{Conclusion}
%─────────────────────────────────────────────────────────────────────────────

This implementation extends PixelChat with a horizontally scaled, performance-aware distributed architecture while fully preserving its existing security properties. The experimental results demonstrate:

\begin{itemize}
    \item \textbf{Throughput:} The load-balanced configuration delivers up to \textbf{2.4$\times$} higher throughput. The LB mixed experiment achieved 492\,RPS versus 206\,RPS for a single backend.

    \item \textbf{Latency:} Median latency is reduced by \textbf{33--57\%} across all workload types. Tail latency (p99) improves most dramatically in mixed workload: from 3,245\,ms to 1,710\,ms (a 47\% reduction), demonstrating that P2C prevents any single backend from becoming a bottleneck.

    \item \textbf{Reliability:} The single-backend mixed configuration drops 2.15\% of requests under 200-worker concurrency. The load balancer eliminates this entirely, achieving a \textbf{0.00\% dropout rate} under the same load.

    \item \textbf{Load distribution:} CPU utilisation plots confirm visible load distribution across all three backends during LB experiments, while single-backend experiments concentrate load on Sys3 alone.

    \item \textbf{Data consistency:} All backends share a single source of truth through Valkey replication. Atomic Lua scripting guarantees exactly-once insertion even when the same \texttt{msg\_id} arrives through multiple backends simultaneously. Three independent layers of deduplication ensure correctness under all failure conditions.
\end{itemize}

The Power of Two Choices algorithm with a composite load score (in-flight requests, CPU, WebSocket connections, Valkey RTT) provides dynamic, performance-responsive routing that satisfies the assignment requirement for load-based backend selection beyond fixed round-robin. The system gracefully handles backend failures by detecting them through the periodic health-check loop and ceasing to route traffic to unavailable nodes.
