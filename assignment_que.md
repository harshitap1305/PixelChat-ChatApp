Deploy and host the application: Extend your previous secure group-chat application and deploy its backend on the 3 allotted systems. Host the application through a Load Balancer, so clients access only the Load Balancer URL/port. Submit the Load Balancer URL; the load generator will be run from our side.
Implement Performance-Based Dynamic Load Balancing: The Load Balancer must dynamically select backends based on system performance/load. When the load of the current backend exceeds a defined threshold, traffic must switch to another suitable backend. Fixed Round-Robin alone is not acceptable. The Load Balancer must also detect unhealthy/unavailable backends and stop routing requests to them.
Optimize the Threshold: Determine an optimal performance threshold for switching between backends. The leaderboard will evaluate all submitted URLs using the load generator and will be updated only at the end of the evaluation period.
Ensure Database Persistence and No Duplicates: All backend servers must use persistent storage and share the same chat data. Every message must have a unique message ID, and the application/database must prevent duplicate insertion when a message with the same ID is received multiple times due to retries, reconnections, or failures.
Required API Routes: The Load Balancer must expose the following exact routes:
/message — accepts "client-name" and "msg" as input and submits a message.
/feed — retrieves all messages.
Students may implement the chatroom/group/place and internal routing of messages in any way they choose, but these two routes and their exact URL paths must be maintained. The submission link will be updated accordingly to use these routes.Load Generation and Evaluation: An official load generator will be operated from our side using the specified API routes.
